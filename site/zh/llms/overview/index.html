    AI Infra

    序言

    当我在2025年3月5号第一次从Wireless Systems 调转60度车头开始接触 AI Systems 这个领域时，我对这个领域很多东西都感到十分陌生，一开始甚至对很多名词都毫无概念。当时恰逢DeepSeek V3 惊艳问世，公司上下针对昇腾上MoE模型推理优化忙成了一锅粥，在某地组织了集中攻关。而我作为一个新人，自然也被召集了过去。但是彼时彼刻，我几乎没有啥大模型推理的经验，仅有的知识也只是做Wireless期间对Transformer模型的一点训练经验，对于 AI Infra 完全陌生。一开始我印象特别深，对于很多几乎是常识性的名词，比如算子，我都不清楚含义。AI 基建时代好像是一列火车不停向前开的火车，没有时间等你停下来慢慢去理解。好在是过程中逐渐干中学，慢慢地对这个领域有了入门的理解。仅以此笔记记录下我在 AI Infra 领域的学习过程，供自己回顾，也希望能帮助到后来者。

    按下发送

    你在对话框中输入“为什么天空是蓝色的？”，选择 GLM-5.2，按下发送。接下来，屏幕上先出现等待提示，随后回答逐渐显示出来。这段时间里发生了什么？

    以一个通过 vLLM 在多张 GPU 上部署 GLM-5.2 的聊天服务为例。应用把你刚输入的话、之前的对话和系统提示词组成请求，发送给服务端。服务端选择一个执行实例，按照模型的对话模板组织文本，再通过 tokenizer 将文本转换为 token ID。模型实际接收的是这串编号。

    所以，你只输入了一句话，这次请求需要处理的内容却可能包含很长的对话历史。从请求构造、路由到执行与返回，完整过程见推理请求生命周期。

    等待执行

    请求到达执行实例时，GPU 可能还在处理其他人的对话。vLLM 的调度器需要决定这一轮处理哪些请求、各处理多少 token，并为执行分配所需的 KV Cache 空间。

    你的请求可能先排队，也可能与其他请求一起组成 batch 执行。有人刚发来一段长 prompt，有人已经在逐步生成回答，两类工作都需要调度。长输入可以拆成多个 chunk，已经结束的请求退出后，新请求再加入。

    这些安排决定了你什么时候开始得到回答，也影响同一组 GPU 能服务多少人。推理运行时展开介绍调度、batching 和显存管理。

    处理输入

    轮到你的请求执行后，模型先处理输入 token，这一阶段称为 prefill。

    Token ID 通过 embedding 转成向量，再经过一层层 Transformer 计算。Attention 让当前位置结合前文信息，前馈网络进一步变换表示。在 MoE 层，路由器为 token 选择专家，由对应专家参与计算。最后，模型给出下一个 token 的分数，称为 logits。

    处理输入时，模型还会保存各层后续 attention 所需的 KV 状态。生成回答时，可以读取这些状态，避免重新计算已有前文的 Key 和 Value。对话越长，需要保存的状态通常也越多，因此历史内容既增加输入处理量，也占用显存。KV Cache讨论这些状态如何存储和复用。

    如果想沿着 GLM-5.2 的实际模型代码看一遍，可以继续读GLM-5.2 推理案例。不同模型的结构差异整理在模型笔记中。

    GPU 上的计算

    上面的每一步还需要变成设备可以执行的工作。矩阵乘、归一化和 attention 等算子由具体的 kernel 实现。Kernel 读取权重和输入，利用片上存储复用数据，驱动计算单元完成运算。

    权重放进显存后，执行时仍需要把数据送到计算单元。一次能处理多少计算、每秒能搬多少数据，是两种不同的限制。硬件介绍这些资源，Roofline 模型则把算力、带宽和算术强度联系起来，解释算子的性能上界。

    在这个多 GPU 部署中，一层计算可能被切到多张卡上，MoE 专家也可能分布在不同卡上。各卡算出的部分结果需要求和，token 需要被发送到所选专家的位置。增加 GPU 因而也引入了传输和等待。并行策略解释计算如何切分，集合通信解释这些数据如何交换与聚合。

    这些 GPU 计算和通信在 prefill 中发生，也会在接下来的生成过程中重复发生。

    回答逐渐出现

    Prefill 得到 logits 后，系统按解码规则选择一个 token。可以选择分数最高的 token，也可以根据调整后的概率分布采样。Temperature、top-p 等参数作用于这一过程，具体见解码与采样。

    选出的 token 随后作为新的输入，与已有 KV Cache 一起参与下一轮计算，产生再下一个 token。这一阶段称为 decode。如此循环，直到产生停止标记或达到输出长度限制。

    生成的 token 会被逐步解码为文本，通过流式响应返回对话框。一个 token 不一定对应一个汉字，界面也可能合并显示多个 token，因此你看到的是一段段增长的文字。

    为了减少逐 token 执行的等待，还可以先生成一段候选 token，再由目标模型批量验证。一次接受多个候选，就能减少生成同样长度回答所需的目标模型执行轮数。这是投机解码要解决的问题。

    你感受到的快慢

    从按下发送到看到第一段回答，包含了请求传输、排队和输入处理等时间。首 token 延迟（TTFT）描述的是从指定测量起点到首个输出 token 的等待。回答开始后，后续 token 的到达间隔则影响阅读时的流畅程度。

    与此同时，服务端还关心同一组 GPU 每秒能为所有用户生成多少 token。更大的 batch 可能提高总吞吐，却不一定让你的回答更快。个人体验与服务容量需要分别衡量，具体定义见指标。

    回答结束后，运行时释放这个请求不再需要的资源，部分前缀缓存可以保留以供复用。你再输入下一句话时，新一轮请求便从这里开始。
